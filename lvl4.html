Multiagentensysteme

Ein Team aus Agenten: Rechte verteilen, Kosten zählen, stille Post erkennen. Dazu A2A.

LVL 4 · Station 1 · Grundlagen

Ein Agent wird zum Tool

Ein Multiagentensystem besteht aus mehreren Agenten, die zusammen eine Aufgabe lösen. Jeder hat

  • eine eigene Rolle (eigener System-Prompt),
  • einen eigenen Kontext (eigener Verlauf: Er sieht nicht, was die anderen erlebt haben),
  • eigene Rechte (eigene Tools).

Technisch ist das im Praxis-Repo überraschend einfach: Ein Agent wird für einen anderen Agenten zum Tool.

def delegations_tool(ziel):
    """Für Multiagentensysteme: Ein anderer Agent wird dem LLM als 'Tool' angeboten."""
    return {
        "name": f"delegiere_an_{ziel.name}",
        "description": f"Gibt eine Teilaufgabe an den Agenten '{ziel.name}' ab. {ziel.beschreibung} "
                       f"Der Agent kennt den bisherigen Verlauf NICHT – formuliere den Auftrag vollständig.",
        "input_schema": {"type": "object", "properties": {"auftrag": {"type": "string"}}, "required": ["auftrag"]},
    }

Ruft der Koordinator so ein „Tool“ auf, startet der Harness einen neuen Agenten mit leerem Verlauf. Dessen Endergebnis kommt als Tool-Ergebnis zum Koordinator zurück. Im Protokoll erscheinen Unteragenten eingerückt:

[AGENT  ] ▶ Agent 'koordinator' startet
[LLM    ] möchte Tool 'delegiere_an_datenbank-analyst' mit {"auftrag": "Berechne den Informatik-Schnitt der 10a."}
    │ [AGENT  ] ▶ Agent 'datenbank-analyst' startet
    │ [MCP    ] tools/call → query_database
    │ [LLM    ] Der Informatik-Schnitt der 10a beträgt 2,05.
    │ [AGENT  ] ■ Agent 'datenbank-analyst' ist fertig (3 Schritt(e)).
[HARNESS] Ergebnis von 'datenbank-analyst' geht zurück an 'koordinator'.

LVL 4 · Station 2 · Interaktiv

Team-Baukasten

Auftrag an das Team: „Schreibe eine kurze Zwischenstand-Rückmeldung für die Klasse 10a in Informatik, die ich vor der nächsten Schulaufgabe an alle verschicken kann.“ Verteile die Rechte, prüfe sie nach dem Prinzip der minimalen Rechte und lass das Team laufen.

Aufträge
  1. Lass das Team mit dem Vorschlag laufen. Um welchen Faktor ist es teurer als ein einzelner Analyst? Woher kommen die vielen Tokens?
  2. Schalte Stille Post ein. Was macht der Analyst falsch? Wer findet den Fehler?
  3. Nimm dem Prüfer query_database weg und wiederhole mit stiller Post. Was steht jetzt in der Rückmeldung an die Klasse?
  4. Gib allen alles. Welche Warnungen erscheinen? Warum ist „mehr Rechte“ kein Vorteil?
  5. Nimm dem Analysten describe_table weg. Was ändert sich im Protokoll und bei den Kosten?
LVL 4 · Station 3 · Vergleich

Muster, Vor- und Nachteile

Die vier üblichen Muster, gezeichnet wie in LangGraph (von Hand nachgebaut). Lies die Kanten: durchgezogen heißt, der Programmierer hat den nächsten Schritt festgelegt, gestrichelt heißt, ein LLM entscheidet zur Laufzeit.

Graphen deuten
  1. Zähle in jedem Muster die gestrichelten Kanten. Ordne die vier Muster auf einer Linie von „Workflow“ bis „Agent“ an.
  2. Vergleiche den Koordinator-Graph mit dem Agenten-Graph aus LVL 1, Station 5. Was entspricht tools?
  3. Wo würdest du beim Erzeuger–Prüfer ein Rundenlimit einbauen? Welche Kante wird dann zur festen Kante zu __end__?
  4. Zeichne ein eigenes Muster: Der Koordinator schickt jeden Bericht zuerst an den pruefer, erst dann darf der autor ran. Welche Kanten werden fest?

✓ Warum mehrere Agenten?

  • Spezialisierung: kurze, klare Prompts statt eines Riesen-Prompts
  • Saubere Kontexte: Jeder startet frisch und wird nicht von Zwischenergebnissen abgelenkt
  • Minimale Rechte: Jeder bekommt nur, was er braucht
  • Kontrolle: Ein unabhängiger Prüfer findet Fehler, die der Ersteller übersieht

✗ Warum lieber nicht?

  • Kosten: Jeder Agent bekommt bei jedem Schritt seinen ganzen Kontext neu
  • Stille Post: Unteragenten kennen den Verlauf nicht
  • Fehlerfortpflanzung: Ein Fehler wandert ungeprüft in den Bericht, wenn niemand prüft
  • Schwer nachzuvollziehen: mehr Agenten, längeres Protokoll

Faustregel: Erst einen einzelnen Agenten bauen. Ein Team nur dann, wenn sich die Aufgaben klar trennen lassen und der Nutzen die Kosten rechtfertigt.

LVL 4 · Station 4 · Erweiterung

Agenten im Netz: A2A

Im Praxis-Repo laufen alle Agenten im selben Harness. Was aber, wenn der Agent einer anderen Schule, eines Schulbuchverlags oder einer Behörde mitarbeiten soll, gebaut mit einem anderen Werkzeug, auf einem anderen Server? Dafür gibt es das offene Protokoll A2A (Agent2Agent), ursprünglich von Google, inzwischen unter dem Dach der Linux Foundation.

Die Agent Card: Visitenkarte eines Agenten

Ein A2A-Agent veröffentlicht unter /.well-known/agent-card.json, wer er ist und was er kann:

{
  "protocolVersion": "0.3.0",
  "name": "Notenstatistik Jakob-Preh-Schule",
  "description": "Beantwortet Fragen zu Notendurchschnitten. Gibt niemals Namen heraus.",
  "url": "https://agenten.schule.example/a2a",
  "version": "1.0.0",
  "capabilities": { "streaming": true },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    {
      "id": "notenschnitt",
      "name": "Notendurchschnitt",
      "description": "Durchschnitt einer Klasse in einem Fach",
      "tags": ["noten", "statistik"]
    }
  ]
}

Ein anderer Agent schickt dann eine Nachricht. Das kennst du aus der MCP-LS: wieder JSON-RPC 2.0.

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "messageId": "msg-001",
      "parts": [{ "kind": "text", "text": "Wie ist der Mathe-Schnitt der 7a?" }]
    }
  }
}

Die Antwort ist oft eine Task (Aufgabe) mit einem Zustand. Längere Aufgaben laufen weiter, während der Auftraggeber etwas anderes tut:

submitted→working→input-required→completed oder: failed · canceled · rejected

Und die Zügel? Bei A2A gibt der eine Agent Arbeit an einen fremden Agenten ab. Dessen Harness, Rechte und LLM kennt man nicht. Der Zustand input-required entspricht unserer Rückfrage (S3). Ob und wo ein Mensch freigibt, muss jede Seite selbst regeln. Darum gilt hier besonders: Vertrauen ist gut, Prüfen im eigenen Harness ist besser. Was ein fremder Agent liefert, sind Daten, keine Befehle.

Code deuten
  1. Woran würde ein Koordinator erkennen, dass dieser Agent für Notenfragen zuständig ist? Vergleiche mit beschreibung in unseren Definitionsdateien.
  2. Welche Felder der Agent Card entsprechen ungefähr tools/list bei MCP?
  3. Die Agent Card sagt „Gibt niemals Namen heraus“. Ist das eine verlässliche Zusage? Wer setzt sie durch?
  4. Bei welchem Task-Zustand wäre eine Freigabe durch einen Menschen sinnvoll?
